# Code review and bug hunt — 2026-10-21

Branch `forge/lan-server`, reviewed from `a1b6749`. The aim was to find what would break or
embarrass at the client site. Scope covered leave and loss-of-pay arithmetic, storage
integrity, backup and restore, sign-in security and route authorisation, the Windows
installer and service scripts (read only, never run), and first-run setup.

## How it was done

- I read the leave core (`usecases/leave.ts`, `usecases/permission.ts`, `packages/domain/src/leave/*`, `jobs/balance.ts`) end to end.
- Three read-only reviewers covered auth and routes, backup and storage, and installer and first-run. I verified every finding of theirs against the code before acting on it. Several were downgraded or dropped (see "Checked and not a bug").
- Every fix started as a test that failed against the old code. Each fix is its own commit with the test beside it. No refactoring for style.
- Test servers ran only on temporary folders through Fastify `inject`, and in the e2e suite on a throwaway folder. `./data` was never touched. Nothing was installed, started or stopped as a Windows service, and no firewall rule or scheduled task was changed.

## Risks found and not fixed

All of these are in `docs/DEFERRED-WORK.md` section 4 with what unblocks them. Most severe first.

1. **The data folder is readable by every Windows user on the host (DW-123).** No ACLs are set and the service runs as LocalSystem. Anyone with a Windows login on that PC can copy the database, the backups and the root CA private key. Every staff PC trusts that key, so holding it allows intercepting their HTTPS. `docs/SECURITY.md` claimed ACLs were applied; it now says they are not. Until this is fixed, nobody who should not see HR data should have a login on the host PC. Not fixed because it is an installer change that can only be verified on a real Windows install.
2. **Firewall rules are open on every network profile (DW-124).** That includes Public, with no subnet scope. A failing `netsh` is ignored and reinstalls add duplicates. Not fixed because the network profile at the client is not known (DW-12). Restricting to private/domain could lock staff out if the office network is classed as Public.
3. **A staged restore waits silently (DW-127).** After "Restore on next start" the panel shows nothing. An unplanned restart days later (a crash, Windows Update) rolls the database back to the backup. The backup is now checked and the safety copy is complete, but the operator still cannot see or cancel the pending restore.
4. **The staff trust `.cmd` is downloaded over plain HTTP (DW-125)** from a name any LAN machine can answer. This is a design issue tied to the CA decision (DW-13).
5. **Upgrading over a running install (DW-126).** The installer does not stop the service before replacing files, and `--prepare` opens the database while the old service may still hold it.
6. **Leave across the leave-year boundary (DW-128).** It is correct with the shipped uncapped carry-forward. With a binding cap it can return days the cap removed. A December request for January is checked against December's balance, so with monthly accrual it may show loss of pay that January's credit would have covered. This needs a company rule.
7. **No screen cancels approved leave (DW-134).** The API works, including the fix above, but no page offers it.
8. **Permission hours accept any date (DW-133).** That includes past dates, weekends, holidays and days already on leave. There is no withdraw and no audit row.
9. **HR can reset a director's password (DW-130).** This is a policy decision. The forced change (fix 6) limits what HR can do with it.
10. **Smaller items:**
    - sign-in reveals which names exist by timing (DW-131)
    - the host-only check follows `X-Forwarded-For` if trust-proxy is ever enabled (DW-132)
    - developer launch scripts are not office-safe (DW-136)
    - the Node download in the installer build is not checksum-verified (DW-137)
    - an uninstall Yes also deletes backups (DW-138)
    - first-run page edge cases (DW-139)
    - login CSRF (DW-140)
    - backup retention counts every `backup-*.db` (DW-141)
    - a missed first month of the leave year is not caught up (DW-135)
    - carry-forward expiry order (DW-129)
    - DW-100 (loss-of-pay confirmation is a yes/no) is unchanged

## Checked and not a bug

- **Append-only ledger and audit.** The database blocks `UPDATE` and `DELETE` on `balance_ledger` and `audit_event`, and no runtime path attempts either.
- **Double approval.** It is blocked by the version check inside the transaction.
- **Rollover and accrual idempotency.** Both have unique rows plus pre-checks, so repeated runs do not double-credit.
- **Concurrency in general.** `node:sqlite` is synchronous on one connection, so transaction bodies do not interleave. The real yields are argon2 and the sign-in delay (fixed in 7) and `bulkProvision`, which runs no transaction.
- **Time zone of "today".** Everything uses the company time zone, not UTC.
- **Restore path traversal.** File names are pattern-checked and the folder is re-resolved.
- **Two backups at once.** File names use milliseconds and `VACUUM INTO` will not overwrite.
- **Sessions.** Idle and absolute expiry are enforced on the server. Every sign-in issues a new token. Sessions are revoked on password change, reset, disable and exit. Cookies are `HttpOnly`, `SameSite=Strict`, and `Secure` under TLS. CSRF is checked on every state-changing API call with a session.
- **One reviewer's claim, downgraded.** The claim was that "a rejection after rollover gives days from nowhere." The hold had already reduced the carried-forward amount, so returning it in the new year is correct with uncapped carry-forward. Only the capped case is wrong (DW-128).

## Claims that are not verified

- **The installer and service scripts were read, not run.** Nothing about installation, service recovery, firewall, TLS trust or LAN access is verified by this pass.
- **Restore was tested on temporary files through `applyPendingRestore` and the host-panel tests.** It was not tested by restarting a real installed service.
- **Fix 11 (setup only from the host) relies on the installed service seeing the operator's browser at `127.0.0.1`.** That matches the installer's desktop shortcut (`https://127.0.0.1:8443/host`), but it has not been tried on a real install.
- **Fix 6 changes what a temporary-password session can do.** The web app shows only the password page in that state, and the unit and e2e suites cover that path. No other client exists.
